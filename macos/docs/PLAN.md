## 顶栏可变模糊（2026-11-18，Claude，测试副本 / 用户决定不采用）

- 经用户同意安装了 Metal Toolchain。SwiftUI `layerEffect` 着色器（公开 API）按像素位置做可变高斯模糊：半径 14pt 到 28pt，之后平滑降到 52pt 为 0；两遍一维采样（单遍网格有点状纹理）。
- 不能加在整页上：macOS 的 SwiftUI ScrollView 是 AppKit 视图，加了 layerEffect 整页空白（即使 isEnabled 为 false）；必须加在各页面的滚动内容上。加上后系统 soft 边缘不再起作用（有无逐像素相同）。
- 概览：绿色保留 22/27（浅/深），文字对比度 5/11；Overlay 50% 为 18/26 与 26/39。逐行模糊会把整行（含可见部分）一起糊掉，不可用。
- 性能（前台，2 轮）：帧节奏与现状相同（含面板开关），但滚动后内存 109 → 235–282MB（整段滚动内容离屏渲染两次），系统 GPU 占用约翻倍，CPU 每 13 秒滚动多约 1 秒。按卡片开关或单遍都更差。内存随页面长度增长，只适合短页面。
- 生产需要编译好的 metallib（`swift build` 不编译 .metal）。正式源码、dist 未改；未提交。报告 `.build/probe/edge/README.md` 第三轮。
- **决定：** 用户以内存和 GPU 代价为由不采用着色器模糊。生产保持原生 soft + `TopRowFade`（100%），dist 不变。测试副本与着色器源码留在 `.build/probe/` 备查。

## 顶栏模糊 vs 不透明度（2026-11-18，Claude，测试副本 / 待用户选择）

- 现在的效果 = 原生 soft（弱、不可调）+ `TopRowFade`（页面底色 100% 不透明到约 40pt），没有额外模糊，所以绿色按钮被盖掉。
- 遮罩降到 75/50/25%：保留的绿色和文字对比度按同一比例回来（G−R 浅色 9/18/28，文字对比度 13/26/38），不透明度无法把两者分开。
- 系统材质（ultraThin、thin、windowBackground）是唯一公开的模糊：文字被糊平、保留部分颜色，但自带约 11 级色调、顶部 15pt 不绘制形成硬边、非活动窗口变成无模糊的灰带，不符合要求。
- 真正的“模糊保留颜色”只剩：页面渲染两遍（大面积重复模糊）或按行位置模糊（逐组件几何监听），都是用户此前排除的。正式源码、dist 未改。报告 `.build/probe/edge/README.md` 第二轮。

## 输入框后方内容柔化（2026-11-17，Claude，用户确认“优化后采用”）

- **背景：** 活动窗口里常规玻璃会把后方清晰的文字透成可读的“鬼影”，玻璃 API 没有模糊强度参数。独立诊断程序比较了 A（无栏）、E/F/G（系统底部栏，soft / automatic / 样式放在栏外，三者完全相同）、H（E + 内容柔化）、I（后方无内容）、J（E + 卡片行）。
  系统底部栏本身让透出减少约 70%；卡片行在深色下透出约为纯文字的两倍；H 再减半。
- **实现：** `SoftenedUnderComposer`：面板里（macOS 26 起）对话的每一行和每张卡片（用户气泡、步骤、思考、理解、查询记录、结果、每张修改卡片、校验、链接）按进入输入框下方的比例模糊（最多 5pt）并变淡（最多 45%），十分之一一档，
  高于 120pt 的视图不处理。按布局计算位置，不用绘制时的 `visualEffect`；直接加在每个视图上，不用逐子视图包装的容器。
- **优化过程（Veer 测试副本，正式曲线，活动窗口）：** 绘制时模糊：内存 110 → 157 MB，开关中位帧 17–20 → 25–28 ms；只淡化：内存同样 157 MB（成本来自 `visualEffect` 本身）；按布局但用包装容器：内存 115 MB，中位帧仍慢（空容器本身就慢 3–9 ms）；
  按布局并直接加在视图上：内存 111–112 MB，CPU 约 +1%。另：中途两个副本因补丁文件名不匹配实际没有打补丁，结果作废并重测。
- **结果（最终源码构建的副本）：** 输入框内透出（滚动后减空对话，均值/95 分位）：浅色 2.17/13 → 1.28/6，深色 8.47/21 → 3.06/9；无内容时两版逐像素相同；输入框旁边距一列没有阶跃。
  面板开关：中位帧 17.6、20.5 ms（正式版 17.1–19.6），最慢 5% 帧 108–118 ms（正式版 102–103），即仍有约 5–16 ms 的增加；流式回复在波动内。
- **检查：** verify.sh 通过（515 项，新增 3 项 `ComposerSofteningTests`）。`dist/Veer.app` 已重建并通过签名校验，含该实现、无测试代码，与验证副本源码一致（除测试入口）；未启动。系统代理关闭，未改动。未提交。

## 启动性能（2026-11-16，Claude，问题 03）

**结论：** 慢的不是内核，是 Veer 启动内核之前准备配置的那几秒。内核本身 25–160 ms 就绪。

**测量方法：** 独立的基准程序调用 Veer 自己的 `VeerProxy`/`VeerCore`，在数据副本上跑（两份真实配置的副本，独立目录，随机端口，随包 Mihomo），
每个阶段用 `ContinuousClock` 计时，就绪用 2 ms 轮询。没有启动 Veer 应用，没有改系统代理或 TUN。每组 10 次（切换配置 5 次，Provider 场景各 3 次，冷 geodata 1 次）。

| 场景（到控制器就绪，ms） | 修改前 P50 / P95 | 修改后 P50 / P95 |
|---|---|---|
| 小配置（74 节点、9263 条规则、7 条“我的分流”修改），首次启动 | 3213 / 3236 | 1138 / 1212 |
| 大配置（247 节点、4110 条规则、1 个 provider） | 4457 / 4652 | 147 / 162 |
| 切换配置后启动（每次新进程），小 / 大 | 未测 | 1099 / 1107，139 / 152 |

修改后到“首次经代理的请求成功”：小配置 P50 1686 ms、P95 1951 ms（修改前 3727 / 4275）。大配置的副本没有带上节点选择记录，默认节点不通，这一项没有数据。

**各阶段（ms，P50，修改前 → 修改后）：** 小配置：应用“我的分流” 2843 → 882，生成运行配置 149 → 35，其余合计约 55 不变；
大配置：生成运行配置 4365 → 63，其余合计约 70 不变。进程创建 0.6，内核从启动到应答：小配置约 165，大配置约 22。

**原因与修改：**
- `ConfigImporter.readableUnicode` 每替换一个 `\U` 转义都从头重新定位，国旗 emoji 多的订阅是平方级：大配置每次启动、每次重载 4.3 秒。改为一次扫描。
- 重放“我的分流”时对每条规则单独做一次 YAML 解析，而 Yams 每次解析都读一遍整个进程环境变量（0.2 ms）：9263 条规则 × 7 条修改。默认编码改为只读一次。
