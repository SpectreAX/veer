## 实现

PanelSplitView 使用 SwiftUI HSplitView 容纳导航及页面与 Agent 两栏。页面、搜索状态和工具栏偏好保持在同一 SwiftUI 树中。AppKit 桥接每帧调用 NSSplitView.setPosition，更新真实分隔位置及 SwiftUI 宿主的布局提案。动画在当前 SwiftUI 提交后启动，避免表格首次列重建提前消耗动画计时。两个子栏及分隔线的宽度之和始终等于容器宽度。

正文不再叠加旧画面。连接表与节点网格预先选择目标列集，内容随着实际栏宽变化；概览采用当前实际宽度，在断点换排。隐藏稳定状态卸载面板内容，关闭时若右栏持有 first responder，先交还窗口。减弱动态效果直接到终态，快速反向从当前分隔位置接续，进入和离开 Agent 页直接切换。

保存的面板宽度异常时沿用 380 点默认值，正常支持 320–520 点；窗口缩放保持面板偏好宽度。原生分隔线代替 AgentPanelColumn 内部重复的分隔线。

## 性能证据的边界

**压力数据更正（续修）**：后续独立审查发现旧 600 行样例重复使用 c0…c5，并非 600 个唯一 ID。它不能支持 SwiftUI Table 与原生表格的性能倍率、选择和复用结论。上述大列表性能数值及相关比较撤回为有效基线；现正换成唯一 ID 重测。静态六行截图和真实分栏中间提案回归测试不受此样例问题影响。

逐帧 setPosition 在 600 连接 / 400 节点压力样例中仍有明显开销，记录过同步调用约 15–74 ms、驱动间隔约 33–75 ms。试过直接分配子视图 frame，可令回调间隔达到 16.7 ms，但原帧显示正文实际只在终点换宽；补发 resize 通知同样未让 SwiftUI 收到中间提案。此方案及其低耗时结论已撤回，最终保留真实更新宿主的 setPosition。新增回归测试能检出这类“几何值改变、正文没有中间布局”的失败。

大列表、首次列重建和端点提交的性能尚未达到完整验收标准。此候选修正已解决已观察到的双层正文、覆盖及焦点风险，但不能宣称动画已在全部场景彻底顺滑。约 16 ms 完整帧门槛仍为 NOT VERIFIED，后续应优化表格与网格的真实布局成本。
